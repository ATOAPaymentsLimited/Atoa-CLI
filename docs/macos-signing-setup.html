Atoa CLI — macOS Code Signing & Notarization Setup

One-time setup of the Apple credentials needed to ship signed, notarized macOS binaries of the atoa CLI. Follow this on the company Mac Mini.

Audience: any engineer. No prior Apple-signing experience assumed. Steps verified against Apple’s current documentation (notarization uses notarytool; the retired altool notarization path is not used).

What you’re producing

By the end you’ll have added 6 secrets to the GitHub repo. That’s the whole goal — the CI workflows already know how to use them.

0 · Prerequisites & access

  • The company Mac Mini, logged in as a user you can access. You’ll create a key in its login Keychain, so do Steps 1–5 on that same machine.
  • Apple Developer account access. Atoa’s team already exists — Team ID 93322BSZUH (“Atoa Payments Ltd”). You need to sign in at developer.apple.com/account.
  • Roles matter (this trips people up):
    • Creating the Developer ID certificate (Step 2) requires the Account Holder role. Admin is not enough for this specific cert type.
    • Creating the App Store Connect API key (Step 6) requires Account Holder or Admin.
    If you don’t have Account Holder, find who does before starting Step 2.
  • Xcode Command Line Tools installed (for codesign / notarytool checks). If xcrun notarytool --help errors, run xcode-select --install first.
Limit to know about

Apple allows a maximum of 5 Developer ID Application certificates per account. Don’t create extras “to test” — reuse the shared one. If the portal already shows a “Developer ID Application: Atoa Payments Ltd” cert and someone has its .p12, you can skip Steps 1–4 and just get that file.

1 Create a Certificate Signing Request (CSR)

On the Mac Mini. This generates the private key (in the login Keychain) and a request file you upload to Apple.

  1. Open Keychain Access (in /Applications/Utilities, or Spotlight-search it).
  2. Menu bar: Keychain Access ▸ Certificate Assistant ▸ Request a Certificate From a Certificate Authority…
  3. Fill the dialog:
    • User Email Address: your Atoa email.
    • Common Name: something identifiable, e.g. Atoa Developer ID.
    • CA Email Address: leave empty.
    • Select “Saved to disk”.
  4. Click Continue and save the file (e.g. to the Desktop). You’ll get a CertificateSigningRequest.certSigningRequest file.

✅ Checkpoint: a .certSigningRequest file exists, and Keychain Access ▸ login ▸ Keys now shows a new private key with the Common Name you chose.

2 Create the Developer ID Application certificate

In the Apple Developer portal (any browser, but stay on the Mac Mini so the next steps line up).

  1. Go to Certificates, Identifiers & Profiles ▸ Certificates.
  2. Click the + (add) button, top-left.
  3. Under the Software section choose Developer ID, then Continue. When prompted for the type, pick Developer ID Application (this signs a Mac app/binary; “Developer ID Installer” is only for .pkg installers — not what we want).
  4. Click Choose File and select the .certSigningRequest from Step 1, then Continue.
  5. Click Download. A .cer file lands in your Downloads folder.

✅ Checkpoint: you have a developerID_application.cer (name may vary) in Downloads.

3 Install the cert & read the signing identity

  1. Double-click the downloaded .cer. It installs into the login Keychain and pairs with the private key from Step 1.
  2. In Terminal, run: 
    security find-identity -v -p codesigning
  3. Find the line that reads Developer ID Application: Atoa Payments Ltd (93322BSZUH). Copy that full quoted string — it is your APPLE_SIGN_IDENTITY.
Where’s the Team ID?

It’s the 93322BSZUH inside the identity string. Our workflow reads the team from that string, so there’s no separate Team ID secret to add.

✅ Checkpoint: find-identity lists exactly one “Developer ID Application: Atoa Payments Ltd …” entry (not “Apple Development” — that’s the wrong type).

4 Export the certificate as a .p12

This bundles the certificate and its private key into one portable file.

  1. In Keychain Access ▸ login ▸ My Certificates, find Developer ID Application: Atoa Payments Ltd. Click the ▸ triangle — you should see a private key nested under it. (If there’s no nested key, the export won’t work — recheck Step 1/3.)
  2. Right-click the certificate ▸ Export “Developer ID Application: …”.
  3. Save as Personal Information Exchange (.p12), e.g. atoa-developer-id.p12.
  4. Set a strong password when prompted. Write it down — this is your APPLE_CERT_PASSWORD.
  5. macOS may ask for your login password to allow the export — that’s expected; approve it.

✅ Checkpoint: an atoa-developer-id.p12 file exists and you know its password.

5 Base64-encode the .p12

GitHub secrets are text, so binary files must be base64-encoded first.

base64 -i atoa-developer-id.p12 | pbcopy

This copies the encoded text to your clipboard — it becomes APPLE_CERT_P12_BASE64 in Step 8. (To verify it worked: base64 -i atoa-developer-id.p12 | wc -c should print a few thousand characters.)

6 Create an App Store Connect API key (for notarization)

notarytool submits the binary to Apple and waits for approval. It authenticates with an API key — not a password.

  1. Go to App Store Connect ▸ Users and Access ▸ Integrations ▸ App Store Connect API.
  2. Make sure you’re on the Team Keys tab (not “Individual/Personal Keys”). Personal keys do not work for notarization.
  3. Click + (Generate API Key). Name it e.g. atoa-cli-notary, and set Access: Developer (sufficient for notarization).
  4. After it’s created, note two values on the page:
    • the key’s Key ID (a 10-character code) → APPLE_API_KEY_ID
    • the Issuer ID shown at the top of the keys list (a UUID) → APPLE_API_ISSUER_ID
  5. Click Download API Key to get the AuthKey_XXXXXXXXXX.p8 file.
You can only download the .p8 once

Apple never lets you re-download it. Save it immediately into the team password manager. If it’s lost, you must revoke the key and make a new one.

✅ Checkpoint: you have the .p8 file, the Key ID, and the Issuer ID.

7 Base64-encode the .p8

base64 -i AuthKey_XXXXXXXXXX.p8 | pbcopy

The clipboard now holds APPLE_API_KEY_P8_BASE64 for Step 8.

8 Add the 6 secrets to GitHub

  1. In the repo on GitHub: Settings ▸ Environments ▸ UAT (this is where GPG_* and AZURE_* already live, so the UAT build can read them).
  2. Under Environment secrets, click Add secret for each of the six, using the exact names below:
NameValue
APPLE_CERT_P12_BASE64base64 from Step 5
APPLE_CERT_PASSWORDthe .p12 password from Step 4
APPLE_SIGN_IDENTITYDeveloper ID Application: Atoa Payments Ltd (93322BSZUH)
APPLE_API_KEY_IDKey ID from Step 6
APPLE_API_ISSUER_IDIssuer ID from Step 6
APPLE_API_KEY_P8_BASE64base64 from Step 7
Why the UAT environment?

So we can test the whole signing + notarization chain on a hotfix/* build before anything reaches main. When you later ship from PROD, the same secrets can be copied to a production environment.

✅ Checkpoint: the UAT environment lists all six Apple secrets.

9 What happens next — testing on UAT

Once the six secrets exist, hand back to the CLI/CI owner. They will:

  1. Add codesign + notarize steps to the macOS UAT workflow (macos-build-uat.yml), which currently builds unsigned.
  2. Push to a hotfix/* branch → the workflow builds, signs, and notarizes the Mac binary and uploads it as an artifact.
  3. On the Mac Mini, download the artifact and verify it passes Gatekeeper: 
    codesign --verify --strict --verbose=2 ./atoa-darwin-arm64
spctl -a -vvv -t exec ./atoa-darwin-arm64   # after adding a quarantine flag, see note below
Why spctl may say “rejected” on a local file

A binary you built/downloaded locally has no com.apple.quarantine flag, so spctl falls back to an offline check that doesn’t recognise bare CLI binaries and prints “rejected”. That is not a real failure. The authoritative signal is that notarytool submit returned Accepted. To simulate a real download:

cp atoa-darwin-arm64 /tmp/atoa-test
xattr -w com.apple.quarantine "0083;0;test;" /tmp/atoa-test
spctl -a -vvv -t exec /tmp/atoa-test

Concepts & safety notes

  • Signing vs notarization. Codesigning stamps the binary with Atoa’s Developer ID (fast, local). Notarization uploads it to Apple for a malware scan and a ticket (slower, online). End users’ Gatekeeper trusts a notarized binary.
  • Bare CLI binaries can’t be “stapled.” Stapling (attaching the ticket to the file) only works for .app/.pkg/.dmg. For a plain binary, Gatekeeper checks Apple’s servers online on first run — this is normal and how gh, deno, etc. work. Our installer also strips the quarantine flag, so curl | sh installs are seamless.
  • The cert is NOT tied to this Mac. It belongs to the Atoa team account. The .p12 is portable — that’s why CI can import it into a throwaway keychain. After Step 5 you could wipe it from the Mac Mini entirely; the vault + GitHub copy are the source of truth.
  • Guard the .p12 + password and the .p8 like signing keys. Anyone with them can sign or notarize software as Atoa. Store them only in the team password manager and GitHub Secrets — never in Slack, email, or a plain repo file.
  • Rotation. If a key leaks or the holder leaves, revoke it in the portal and generate a replacement. Because these are team-level assets, that doesn’t depend on any one device.
